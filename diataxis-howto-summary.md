# Diátaxis How-To Guide — Guidelines

Standalone summary of <https://diataxis.fr/how-to-guides/>. Guidelines a how-to guide must follow to comply with the Diátaxis definition.

---

## 1. Definition

A how-to guide is **goal-oriented directions that take a competent user through a real problem toward a specific result**. It guides *action*, not learning.

Canonical analogy: **a recipe**. Defines what will be achieved, addresses one specific question, omits teaching/discussion, focuses only on how to make the dish.

## 2. Guidelines

### 2.1 Purpose & framing

- Goal-oriented: addresses a specific real-world problem or result, not an open-ended skill area.
- Written from the user's perspective, not the perspective of the machinery/system.
- Solves a problem the user actually has (purpose + need), not merely a documentation of what a tool can do.
- Not a tutorial: does not teach foundational concepts, does not walk a beginner through learning.
- Not reference: does not exhaustively describe the machinery; links out to reference material instead.
- Not explanation: does not digress into theory, history, or discussion.

### 2.2 Audience assumptions

- Assumes an already-competent user who knows what they want and can follow instructions correctly.
- Does not explain basic mechanical operations a competent user is expected to know (e.g., "click the button", "open the terminal").

### 2.3 Content

- Action-only: contains directions, not teaching, not lengthy explanation, not digression.
- Practical usability over completeness: covers what the user needs to act, not every detail.
- References external reference/explanation docs rather than inlining them.

### 2.4 Structure & flow

- Logical sequence in time: each step depends on the previous where applicable; order is meaningful.
- Adaptable: applies to a range of real-world cases, not one narrow context-specific instance.
- Not a rigid procedure when the problem doesn't reduce to one: may include branches, choice points, multiple entry/exit points, user judgment.
- Starts and ends at reasonable, meaningful boundaries; user joins it to their own work.
- Respects user cognitive flow: avoids unnecessary context switches; resolves held thoughts in reasonable time.

### 2.5 Language

- Opens with intent, e.g. **"This guide shows you how to …"**.
- Uses conditional imperatives where choice exists, e.g. **"If you want X, do Y"**.
- Imperative voice for actions.

### 2.6 Title / naming

- Title is specific and names the problem solved, e.g. **"How to integrate application performance monitoring"**.
- Title is NOT vague, open-ended, or skill-domain-wide (e.g. **"How to build a web application"** fails — too open-ended).
- Title aids search and human scanning.

### 2.7 Scope

- Tackles a single, specific problem or task.
- Does NOT attempt to cover an entire skill domain in one document.

## 3. Quick discriminators

- "Teaches a beginner" → tutorial, not how-to.
- "Lists every option" → reference, not how-to.
- "Explains why / discusses" → explanation, not how-to.
- "Directs a competent user to a specific result" → how-to.
